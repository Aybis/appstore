# MAYA API

NestJS REST API: auth, catalog, publishing, signed downloads and the
version-check that shipped apps call on launch. PostgreSQL holds the data;
every tenant table has row-level security, so one organization can never read
another's rows.

## Structure

```
apps/api/
├── database/
│   ├── setup-local.sh          create roles + databases on local Postgres
│   ├── bootstrap-local.sql     app_runtime role (used by setup-local.sh)
│   ├── grants-local.sql        schema grants (used by setup-local.sh)
│   └── bootstrap-supabase.sql  the same role on a Supabase project
├── drizzle/                    SQL migrations, generated by drizzle-kit
├── scripts/                    seed-demo, seed-member, ingest-binaries, ...
├── src/
│   ├── main.ts                 boot: load .env, Sentry, Nest
│   ├── app.module.ts           wires every module + global guards
│   ├── config/                 env.ts (validated with zod), load-env.ts
│   ├── database/               Drizzle schema, postgres client, withTenant()
│   └── modules/                one folder per feature
│       ├── account/            your own profile: /v1/me (name, avatar, password)
│       ├── auth/               login, refresh, JWT + roles guards, API keys
│       ├── catalog/            list / search / detail / download / version-check
│       ├── publish/            create apps, upload builds, testers
│       ├── members/  orgs/  audit/  dashboard/  devices/
│       ├── client/             the MAYA app's own download page + updates
│       ├── distribution/       Android + iOS (itms-services) install adapters
│       ├── storage/            file storage: local disk or S3/R2
│       └── health/
└── test/                       e2e tests (real Postgres, no mocks)
```

A module holds its controller, service and tests side by side
(`catalog.controller.ts`, `catalog.service.ts`, `version.spec.ts`).

## Run locally

All commands run from the **repo root**.

### 1. PostgreSQL 17 on port 5433

```bash
brew install postgresql@17
sed -i '' 's/^#port = 5432.*/port = 5433/' /opt/homebrew/var/postgresql@17/postgresql.conf
brew services start postgresql@17
```

5433, not 5432, so it never clashes with another Postgres on the machine.

### 2. Database, env, migrations, seed

```bash
pnpm install
cp .env.example .env   # already points at localhost:5433
pnpm db:setup          # roles + appstore and appstore_test databases
pnpm db:migrate        # runs as MIGRATION_DATABASE_URL (the schema owner)
pnpm db:seed           # org "maya", 4 apps, login demo@maya.app / demo1234
```

The seeded builds are a few KB of filler: download links work, but a phone
will refuse to install them. Load real files with
`pnpm --filter @appstore/api ingest -- /path/to/apks --org maya`.

### 3. Start

```bash
pnpm dev:api                         # watch mode on http://localhost:3000
curl localhost:3000/health           # {"status":"ok"}
```

Always start through the Nest CLI (`pnpm dev:api`), never `tsx src/main.ts`:
tsx skips decorator metadata and Nest's dependency injection fails.

## File storage

Builds, icons and the MAYA download manifest live in one store: the `store/`
folder locally (`BLOB_STORE=fs`), a Cloudflare R2 bucket in production
(`BLOB_STORE=s3`). Each build is stored **once**, and its path says which
release it is:

```
<org-slug>/<app-slug>/<platform>/<app-slug>-<version>-<sha8>.<apk|ipa>
maya/hr-portal/android/hr-portal-3.2.1-624b51b7.apk     ← artifacts.storage_key
icons/<sha256>.png                                       ← apps.icon_key
avatars/<sha256>.png                                     ← users.avatar_key
client/manifest.json                                     ← the MAYA download page
```

- `artifacts.storage_key` is the link from the database to the file. Every
  download reads it.
- Uploading the same bytes again (even as another version) reuses the
  existing file instead of storing a second copy.
- A version that already exists is refused **before** anything is written,
  so a rejected upload leaves nothing behind.
- "Publish as MAYA app" in the console writes `client/manifest.json`,
  which points at that release's file. Nothing is copied.
- Tests always use the local disk, never R2 (`vitest.config.ts`).

`storage:tidy` brings an existing store into line. It moves old files into
this layout, repoints the MAYA client at its release, and lists files nothing
references (old copies, folders left by test runs). Run it without `--apply`
first and read what it plans. It works on whatever database and bucket the
env file names: `.env` (dev) by default, `.env.production` with the `:prod`
scripts. From the repo root:

```bash
pnpm storage:tidy                 # dev: report only
pnpm storage:tidy:prod            # prod: report only
pnpm storage:tidy:prod --apply    # prod: move, then delete orphans
```

If most of the files the database needs aren't in the store, it deletes
nothing: that means the env points at a database and a bucket that don't
belong together.

## Database changes

1. Edit the schema in `src/database/*.schema.ts`.
2. `pnpm --filter @appstore/api db:generate` writes a new SQL file to `drizzle/`.
3. `pnpm db:migrate` applies it.

Never edit a migration that has already run anywhere: add a new one.

## Tests

```bash
pnpm --filter @appstore/api test
```

Unit tests (`src/**/*.spec.ts`) and e2e tests (`test/*.e2e-spec.ts`) run
together. The e2e tests need the local Postgres above: they migrate
`appstore_test` and create a scratch schema per file.

## Scripts

| Command (`pnpm --filter @appstore/api …`) | What it does |
|---|---|
| `db:seed -- --org acme --email me@acme.test` | seed a different org/login |
| `db:seed:member -- <org> <email> <password> [role]` | add a login to an org |
| `db:seed:telemetry -- --org maya` | demo installs for the dashboard |
| `ingest -- <folder> --org maya` | load real APK/IPA files |
| `storage:tidy` / `storage:tidy -- --apply` | report / fix the file store (see below) |

Production database migrations run from the repo root with `pnpm db:migrate:prod`,
which reads `.env.production`.
